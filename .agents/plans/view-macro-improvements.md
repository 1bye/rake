# Plan: `rake::view!` improvements

Handoff plan for improving the experimental `rake::view!` macro. Work the phases
in order: Phase 0 builds the safety net that every later phase relies on. Each
phase is meant to land as one reviewable change.

## Before you start

- Read `AGENTS.md`, `.agents/workflow/rust/AGENTS.md`, `testing.md` and
  `rustdoc.md` in that folder. Follow their spacing and verification rules.
- Run `git status`. The working tree may already contain the owner's
  uncommitted edits (at the time of writing: `docs/rake-inspector.md` and
  `examples/inspector/src/{appearance,input,tree,view}.rs`). Do not revert or
  reformat them. If a phase forces a migration in one of those files, make the
  smallest edit you can and say so in your report.
- The API is experimental and may break, but every in-repo consumer must be
  migrated in the same change: `examples/view`, `examples/inspector`,
  `crates/rake/src/overlay.rs`, `crates/rake/tests/view*`,
  `tests/renamed-facade`, and the doc examples in `docs/experimental-view.md`,
  `docs/experimental-overlays.md` and `docs/devtools.md`.
- Keep the two contracts in sync on every behavior change: the rustdoc on
  `pub fn view` in `crates/rake-macros/src/lib.rs` and
  `docs/experimental-view.md`.
- GPUI is `gpui_ce` at rev `99109e3`. Check that every builder method you emit
  exists in `~/.cargo/git/checkouts/gpui-ce-*/99109e3/crates/gpui/src`. Most
  style methods are generated by `crates/gpui_macros/src/styles.rs`.

### Decisions for the owner (confirm before the phase that needs them)

1. **Phase 0:** may `trybuild` be added as a dev-dependency of `crates/rake`?
   It changes `Cargo.lock`. Without it, Phase 0 covers diagnostics with
   unit-level `syn::Result` checks only.
2. **Phase 5:** event naming. Recommended: `on:click` etc. as the canonical
   names, with the old `onclick` names still accepted and flagged as
   deprecated. The alternative is a hard rename.
3. **Phase 2:** headings become text-only, the same as `p`. Headings that embed
   arbitrary elements become compile errors and are migrated to `div` with a
   heading role.
4. **Phase 7:** the syntax for bare boolean attributes, prop shorthand and
   default fields, as proposed below.

### Verification commands (run for every phase)

```sh
cargo test -p rake-macros --locked
cargo test -p rake --features experimental-view --test view --test view_components --test view_paragraphs --locked
cargo test -p rake --features view-test-support --test view_state --locked
cargo test -p rake --features experimental-view --doc --locked
cargo check -p rake-view -p rake-inspector -p renamed-facade --all-targets --locked
cargo check -p rake-view -p renamed-facade --lib --target wasm32-unknown-unknown --locked
cargo clippy -p rake-macros -p rake --features experimental-view --all-targets --locked
```

Confirm the inspector package name in `examples/inspector/Cargo.toml`. Add the
UI-test command from Phase 0 once it exists. Report which checks ran and which
you couldn't run.

## Phase 0: Test safety net

**Goal:** lock in the current expansion output and diagnostics so the later
refactor and fixes are provably safe.

1. **Expansion snapshots** in `crates/rake-macros/src/view/tests.rs`, with no
   new dependency:
   - Add a fixture list of about 12 representative inputs: containers, `p` with
     inline runs, headings, buttons with `disabled`, `focus` and `tabindex`,
     `img`, `<view entity>`, components (self-closing and paired), `if`/`else
     if`, `for`, `on:Action`, `tab-navigation`, and every `class` utility.
   - For each fixture, compare `expand(source).to_string()` with
     `src/view/snapshots/<name>.txt`. Set `RAKE_UPDATE_SNAPSHOTS=1` to rewrite
     the files.
   - Commit the snapshots generated from current `main`.
2. **Diagnostic UI tests** (if decision 1 is yes):
   - Add `crates/rake/tests/view_ui.rs`, gated on
     `#![cfg(feature = "experimental-view")]`, which runs
     `trybuild::TestCases::new().compile_fail("tests/ui/view/*.rs")`.
   - Add one file per existing diagnostic: missing closing tag, mismatched
     closing tag, duplicate attribute, unsupported tag, unsupported attribute,
     unsupported utility, dynamic `class`, `img` without `alt`, loop root
     without `id`, text directly inside a loop, an owned `entity`/`focus`/`scroll`,
     `disabled` on a non-button, a block element in `p`, an inline `id` in `p`,
     component `children` combined with a paired tag, and a non-ident component
     prop.
   - Generate the `.stderr` files with `TRYBUILD=overwrite`. Check them by hand:
     each must point at the offending token.
   - Add the run command to "Example and checks" in `docs/experimental-view.md`.

**Done when:** all snapshots and UI tests pass on unchanged macro code.

## Phase 1: Refactor expansion into a per-tag table (no behavior change)

**Goal:** replace the 250-line string-matching `Element::expand`
(`crates/rake-macros/src/view.rs:392-640`) with resolved tags, so later phases
can add tags and attributes in one place.

1. Add `crates/rake-macros/src/view/tag.rs` with
   `enum Tag { Container, Paragraph, Heading(u8), List, ListItem, Button, Image, Entity, Component }`.
   Resolve it once during `Element::parse`, store it on `Element`, and keep the
   original `syn::Path` for spans and components. Unknown lowercase tags still
   fail with the same message, now at parse time.
2. Give each tag the table data it needs:
   - its base builder tokens (the current `match tag.as_str()` arms)
   - whether it composes text (`Paragraph`)
   - whether it supports `disabled` (`Button`)
   - whether it gets an automatic label (`Button`, `Heading`)
   - which tag-specific attributes it accepts: `src`/`alt` for `Image`;
     `wrap`/`ellipsis`/`max-lines` for `Paragraph`
3. Split `expand` into `base_builder`, `apply_attributes`, `apply_focus` and
   `expand_children_into`, keeping the current order of emitted calls exactly.
4. Remove the three `quote!(#path).to_string().replace(' ', "")` repetitions;
   the tag carries a display name.
5. Simplify `require_loop_ids` and `expand_children`. Give `Node::Text` and
   `Node::Expression` separate match arms instead of the nested
   `match`/`unreachable!()`.
6. In `crates/rake/src/view.rs`, extend the duplicate-ID panic message (around
   line 59) with a hint: "if this comes from a helper rendered more than once,
   pass a distinct root id into it". Update the matching `view_state` test
   expectation if one asserts the message.

**Done when:** the expansion snapshots are byte-identical, UI test stderr is
unchanged apart from the improved panic hint, and all verification commands
pass.

## Phase 2: Text composition for headings

**Problem:** headings lower to `div().flex().flex_col()`, and every
text/expression child becomes its own `gpui::Text`. So `<h2>"Count: "{n}</h2>`
renders on two lines, and `strong`/`em` aren't allowed inside headings.

1. Lower `h1`–`h6` through the paragraph path (`view/paragraph.rs`,
   `expand_paragraph`), with the heading builder as the base: heading role,
   `aria_level`, default size, bold, and `min_w_0`. Keep the default sizes
   30/24/20/16/16/16.
2. Headings accept the same inline content and attributes as `p`: text,
   `{AsRef<str>}`, `span`, `strong`, `em`, `br`, `if`, `for` (once Phase 7
   lands, `match` too), plus `wrap`, `ellipsis` and `max-lines`.
3. Accessibility:
   - Check that the composed text node exposes the full heading text. Look at
     how `ParagraphContent::finish` builds its accessible node in
     `crates/rake/src/view/paragraph.rs`.
   - If it does, drop the literal-only `aria_label` generation for headings.
     Otherwise derive the label from the composed text at runtime.
   - An explicit `aria-label` still wins.
   - Add a `view_state` frame test that asserts the AccessKit node: heading
     role, level, and the full text of a mixed literal and dynamic heading.
4. Headings with element children (components, `{icon(..)}`, `div`) now get a
   compile error: "headings compose text like p; use a div with
   role={Role::Heading} for rich content". Grep every consumer for `<h[1-6]` and
   migrate any that break.
5. Tests:
   - a `view_paragraphs`-style test that a mixed heading is one text layout
   - a UI test for the new rejection
   - updated snapshots, an expected change to review in the diff
6. Docs: update the tag table, "Paragraph composition" (now "p and headings"),
   add a migration note, and update the rustdoc.

Buttons stay as they are. Their row layout already keeps mixed children inline,
and they legitimately hold icons.

**Done when:** a mixed literal and dynamic heading renders on one line with
inline `strong`/`em`, and its accessible name equals the full text.

## Phase 3: Multiple diagnostics and IDE resilience

**Problem:** parsing and expansion stop at the first error, and the whole
output is replaced by `compile_error!`. rust-analyzer then loses completion
inside every `{expr}` in the invocation.

1. **Collect expansion errors.** Thread an error accumulator, for example a
   `Diagnostics { errors: Option<syn::Error> }` with `push` (using
   `syn::Error::combine`) and `finish`, through `expand`, component, paragraph
   and class expansion. Wherever the code returns `Err` for a local problem
   (bad attribute, bad utility, missing `alt`, loop `id`), record the error and
   keep going.
2. **Keep user expressions visible to the IDE.** When expansion produced errors,
   emit the combined `compile_error!`s together with a block that still
   type-checks every user expression the macro saw: attribute values, children,
   conditions, iterators, and loop bodies with their patterns bound. For
   example:

   ```rust
   { compile_error!(...); #[allow(unreachable_code, unused)] if false { /* exprs */ } ; ::core::unreachable!() }
   ```

   Check the trybuild stderr. If this causes noisy secondary type errors (for
   example, closure inference failing for `cx.listener` outside its builder),
   wrap each expression in `let _ = || { expr };`, or emit only the expressions
   that are plain paths or field accesses. Choose whatever keeps the stderr
   down to the real errors, and record the choice in a comment.
3. **Recover from parse errors at the element level.** When an attribute fails
   to parse, record the error and skip ahead to the next attribute name, `>` or
   `/`, so later attributes and children are still checked. Leave it at that;
   full markup recovery isn't needed.
4. **Tests:**
   - a UI test with three independent errors in one invocation, expecting three
     diagnostics
   - a UI test showing that a type error inside `{expr}` is still reported at the
     expression when a sibling attribute is invalid
5. Manual check, noted in your report: in an editor using rust-analyzer, add an
   invalid utility to one element in `examples/view` and confirm completion
   still works inside a sibling `onclick={...}`.

**Done when:** independent errors in one invocation are all reported, and user
expressions stay type-checked next to macro errors without extra noise.

## Phase 4: Utility coverage and conditional classes

### 4a. Utilities

These are the methods real code currently writes in `style` closures (see
`examples/inspector/src/view.rs`). Add each one to `class_methods` in
`view.rs`, check the GPUI method exists, and document it:

| Utility | GPUI method |
| --- | --- |
| `shrink-0` | `flex_shrink_0` |
| `grow` | `flex_grow_1` (confirm it exists; `flex_grow(f32)` takes an argument) |
| `grow-0` | `flex_grow_0` |
| `flex-none` | `flex_none` |
| `relative`, `absolute` | from `position_style_methods` |
| `items-stretch` | `items_stretch` |
| `self-start`, `self-center`, `self-end` | confirm each |
| `justify-around` | `justify_around` |
| `truncate` | `truncate` |
| `whitespace-nowrap` | `whitespace_nowrap` |
| `overflow-x-hidden`, `overflow-y-hidden` | confirm |
| `border-t`, `border-b`, `border-l`, `border-r` | `border_t_1`, `border_b_1`, ... |
| `border-{t,b,l,r}-{0,1,2}` | from `border_prefixes`/`border_suffixes` |
| `gap-x-N`, `gap-y-N` | same spacing scale as `gap` |
| `w-N`, `h-N`, `size-N` | same spacing scale (confirm the generated names) |

- Restructure `class_methods` as one data table, `(utility, method)` pairs plus
  the spacing-scale generator. The docs list should then be checkable against
  it: add a unit test that every utility named in the docs bullet list expands
  successfully. Parse the list from the doc file, or keep a shared const that
  both use.
- Add a compile test in `crates/rake/tests/view.rs` that applies every
  supported utility to a real `div`, so a GPUI rename breaks the build.
- Utility errors should keep naming the specific class (`LitStr` subspans
  aren't available on stable).

### 4b. Conditional classes: `class:<utility>={bool}`

- Parsing: allow `class:` as a second namespace next to `on:` (`view.rs:150`).
  The part after the colon is a utility name that may contain hyphens, joined
  the same way hyphenated attribute names are. Duplicate detection uses the
  full name.
- Expansion: `.when(#cond, |s| s #methods)` with the utility's methods from 4a,
  applied in attribute order like other styling.
- Paragraph inline tags: support `class:<inline-utility>={bool}` with
  `.when`-style logic on the run style. Otherwise reject it with a clear
  message; either is fine, but document which.
- Tests: an expansion snapshot, a `view.rs` test showing the style is applied
  only when true, and UI tests for an unknown utility and a non-literal name.

**Done when:** most inspector `style` closures could switch to classes. Don't
migrate the inspector in this phase; it has uncommitted edits.

## Phase 5: Events

**Recommended per decision 2:** canonical `on:<event>` names. Lowercase means a
built-in event; a path whose last segment is uppercase means a typed action
(current behavior).

| Attribute | GPUI call |
| --- | --- |
| `on:click` | `on_click` |
| `on:key-down`, `on:key-up` | `on_key_down`, `on_key_up` |
| `on:mouse-move` | `on_mouse_move` |
| `on:mouse-down`, `on:mouse-up` | left button (current) |
| `on:right-mouse-down`, `on:right-mouse-up`, `on:middle-mouse-down`, `on:middle-mouse-up` | `MouseButton::Right` / `Middle` |
| `on:any-mouse-down` | `on_any_mouse_down` |
| `on:mouse-down-out`, `on:mouse-up-out` | `on_mouse_down_out`, `on_mouse_up_out` (check `on_mouse_up_out`'s signature) |
| `on:hover` | `on_hover` (`&bool`) |
| `on:scroll-wheel` | `on_scroll_wheel` |
| `on:drop` | `on_drop::<T>`, with `T` inferred from the closure's annotated parameter; document that the annotation is required |
| `on:drag={(value, constructor)}` | `on_drag(value, constructor)`; destructure the tuple in the expansion |
| `tooltip={builder}` | `tooltip` (an attribute, not an event) |

- Disabled buttons: gate every `on:*` event the same way as today (the
  `starts_with("on")` check at `view.rs:582`). Gate `tooltip`? No: disabled
  controls often explain themselves through tooltips. Document this.
- Legacy names (`onclick`, `onkeydown`, `onkeyup`, `onmousemove`,
  `onmousedown`, `onmouseup`):
  - With deprecated aliases: keep expanding them, and emit a warning by
    referencing a hidden `#[deprecated(note = "use on:click")]` const in
    `rake::__private`, spanned at the attribute. Migrate every in-repo
    consumer.
  - With a hard rename: reject them with a "renamed to on:click" error.
- Unknown lowercase `on:foo` gets an error listing the supported events.
- Tests:
  - `view_state` frame tests for right-click, hover enter/leave and scroll-wheel
    dispatch
  - an expansion snapshot covering every event
  - UI tests for an unknown event and for the deprecation warning (trybuild
    `pass` cases don't show warnings, so either assert the warning via a
    `compile_fail` case with `#![deny(deprecated)]`, or test it at unit level)

**Done when:** every row of the table is covered by a test, and the inspector
and examples compile with no deprecation warnings.

## Phase 6: Elements

1. **`svg`:** `<svg path="icons/search.svg" aria-label="Search" class=.. style=../>`
   lowers to `gpui::svg().path(..)`.
   - Check what `Svg` (`crates/gpui/src/elements/svg.rs`) implements. If it
     isn't `StatefulInteractiveElement`, don't emit `.id`, document that, and
     exempt `svg` from the loop-`id` rule. Otherwise treat it like other tags.
   - Accessibility: decorative (no role) unless `aria-label` is given. Mirror
     how `img` handles `alt=""` in `crates/rake/src/view.rs`.
   - Rejects children.
   - Look at the inspector's `icon(Icon::.., color)` helper to check the API
     covers it (color through `style={|s| s.text_color(..)}`).
2. **Semantic containers:** `nav`, `header`, `footer`, `main`, `aside`,
   `article`. Each is a `Container` plus an AccessKit role. Confirm the role
   names exist in the vendored `accesskit` version (`Navigation`, `Banner`,
   `ContentInfo`, `Main`, `Complementary`, `Article`). Drop any that have no
   role rather than inventing one.
3. **`hr`:** a self-closing full-width, 1px-high container. Use a separator role
   only if `accesskit` has one. Rejects children.
4. Tests: expansion snapshots, `view.rs` tests that check roles via
   `accesskit`, a UI test for `svg` with children, and doc table rows.

## Phase 7: Syntax additions

1. **`match` children:**
   `match expr { Pat if guard => { nodes } ... }`. Arm bodies must be braced
   node lists, and a trailing comma is optional.
   - Supported in containers, component children and paragraph/heading inline
     content.
   - `require_loop_ids` recurses into arms like it does for `if` branches.
   - Expansion mirrors `If` in `expand_children` and in `inline_children`.
   - Tests: a runtime test that only the matched arm is evaluated, the
     loop-`id` rule inside arms, and a guard.
2. **Bare boolean attributes:** `<button disabled>` and `<p ellipsis>` mean
   `={true}`. In `Element::parse`, if `=` doesn't follow the name, the value is
   the literal `true`. Accept this only for attributes that are boolean
   (`disabled`, `wrap`, `ellipsis`, `tab-navigation`, `aria-expanded`) and for
   component props (`<Badge compact/>` becomes `compact: true`). Other names get
   "attribute `x` requires a value".
3. **Prop shorthand:** a braced bare identifier in attribute position, `<Card {id}/>`,
   means `id={id}`. It works for components and for built-in attributes whose
   name is a valid identifier.
4. **Component defaults:** `<Card id={x} {..Default::default()}/>`. It must be
   the last attribute, components only. It expands to `..expr` after
   `children` in the struct literal. Reject it on built-in tags and when it
   isn't last.
5. Tests: snapshots, runtime tests, and UI tests for every rejection. Update
   "Typed components, children and slots" (replacing the "Supply None
   explicitly" sentence with the defaults option), and "Conditions, loops and
   identity".

## Phase 8: Docs and formatting guidance

1. Add a "Formatting" section to `docs/experimental-view.md`: rustfmt doesn't
   format macro bodies. Recommend one attribute per line once a tag has more
   than about three attributes, and extracting long `style` closures and
   listeners into named `let` bindings or methods. Show one inspector-style
   before/after.
2. Reread the whole doc and rustdoc for consistency after Phases 2–7, then
   update "Current limits".
3. Note a follow-up, not in this plan: a `leptosfmt`-style formatter for
   `view!` bodies.
